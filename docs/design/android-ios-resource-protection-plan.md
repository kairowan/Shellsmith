# Android 与 iOS 资源保护迭代实施计划

状态：APK、AAB 多模块与 iOS 主应用的业务资源授权已实现，并加入运行时事件关联、范围读取和 App Group 交接。正式签名、商店下发及实际业务验收分开记录。分支 `feat/android-ios-resource-protection`，基线 `7a6b2ec`，发布对照为 Shellsmith v1.11.0。[当前资源协议及正式验收输入](protected-resource-protocol.md)

## 目标与首个交付

- Android 与 iOS 各选一份自有的规则或 JSON 资源。在构建时把它转成认证密文，在设备首次访问资源时，通过用户已有的 BYOS 服务授权。一次授权的范围限于一个应用构建中的指定资源组。
- 用最终签名 APK 和 IPA 证明必保资源已变换、明文原件已移除、授权后业务读取正确。证明错误授权、密文篡改和过期授权得到预期结果。
- 记录资源请求阶段的安全信号、授权决定和真实读取结果，让应用方能区分设备环境异常、服务异常和资源验证失败。
- 首版以 Android 单 APK 的既有设备批准模式（API 24 起）和 iOS 主应用的 App Attest（iOS 14 起且设备支持）为目标。Android AAB、扩展 target、随机访问媒体、模型及直接文件描述符路径，在各自的读写和分发证据具备后扩展。Android 4.4、iOS 13 和现有离线功能沿用已发布的流程。

## 基线与落点

| 链路 | 已有实现 | 本次接入点 |
|---|---|---|
| Android 构建 | `protect_apk` 驱动解包、资源变换、重打包。`transform_assets` 调用内置 Packer 的 `assets-transform`，以现有 IKM 派生 PAS2 密钥。 | 在 `crates/shield-core/src/protect_api.rs` 和 `protect/xop_pvm2.rs` 的资源阶段协调显式清单，先判定必保项的归属，再执行各自的变换。`protect/runtime_metadata.rs` 校验 Packer/壳能力匹配。 |
| Android 读取 | `MocikaAssets` 有流式 `open`、落盘 `openFd` 及 Native overlay。`assets_pas2.rs` 持有当前进程所用的 PAS2 密钥。 | 新资源使用显式的异步授权与流式读取入口。现有 `open/openFd/getAssets` 继续处理原有资源。 |
| BYOS | Android DEXB v7 启动经 `/v1/keys/*` 获取产物级 IKM。自有服务已有批准、撤销、轮换、备份恢复。 | 资源授权采用新命名空间，复用身份验证和密钥封存，按资源组查询。服务端仓库独立，客户端文档和协议测试向量对两个实现共同生效。 |
| iOS 构建与读取 | `shield-ios` 在工作副本接入 Swift Package，随后 Archive、Export，校验签名、Entitlements 等。 | `crates/shield-ios/src/lib.rs` 在 Archive 前完成资源处理。`project_patch.rs` 接线 Swift 读取代码与密文。`archive_verify.rs` 增加项目配置启用后的最终产物检查。 |
| 运行时信号 | Android 有 `RuntimeSecurity` 和 `MocikaUi`。iOS 有 `ShellsmithRuntime` 威胁回调及 App Attest 客户端。 | 在资源读取和 BYOS 授权层关联已有信号，并记录服务器的实际决定。 |

当前 PAS2 说明、密钥边界和 iOS 流程分别见[资源保护](asset-protection.md)、[BYOS 密钥模型](byos-key-model.md)和[iOS 加固](ios-hardening.md)。

## 设计决策与约束

### 资源标识和构建契约

- 首版使用版本化的构建清单。每项包含资源 ID、源相对路径、资源组、读取方式。初期只有流式读取，所有清单项均为必保。Android 相对 `assets/`，iOS 相对明确的主应用资源目录和 target。资源 ID 稳定，产物 ID 按构建生成。运行时用 ID 查找密文，路径只供本地构建和验收使用。
- 预检拒绝空清单、重复资源 ID、文件缺失、目标冲突、路径逃逸、大小超限及无法确认打包归属的项。检查符号链接和文件类型。对大小写不敏感的 iOS 构建环境核对规范化后的路径冲突。原输入、工程和签名材料留在原处，所有删改在独立暂存或工程工作副本内执行。
- 对于 Android 严格模式，必保清单优先确定资源归属，再运行启发式 PAS2 选取与调用点改写。核验同一资源只有一个有效读取路径。仍通过旧资源 API 或第三方 SDK 读取的必保项，在验证兼容前拒绝出包。对于 iOS，工作副本同时检查 Copy Bundle Resources、Swift Package 资源、整目录复制和目标成员关系。验证 Archive 与最终 IPA，覆盖可能再次打入包内的原件。
- 复用项目现有的 AES-GCM 实现或系统加密库，两个平台共享格式规范和固定测试向量。新容器有独立版本和边界检查。规范确定字节序、认证标签、Nonce 唯一性、分片长度与上限。认证数据绑定应用构建、资源组、资源 ID、资源版本、分片序号和总长度。每片通过认证后才交付字节，结尾验证总长度和分片数。截断、换片、重排、重复或跨资源替换均失败。
- 最终校验检查目标条目、版本、密文摘要、明文原路径及可能的重复打包位置。仅比较魔数或文件数不足以判定通过。用可识别的测试原件覆盖内容残留检查，报告写入最终包摘要、资源 ID、密文摘要和核验状态。文件系统路径和原件内容留在本地测试证据里。
- 取舍：独立读取入口要求应用集成一次，能把必保范围、失败行为和授权时点定义清楚。等实际业务需要兼容第三方读取接口时，再对指定接口加适配。

### 密钥与授权契约

- 每个应用构建的每个资源组使用独立随机数据密钥。服务按租户、应用身份、构建、资源组和资源版本封存及查询。旧产物 IKM 继续支撑原启动链。密钥可用范围由服务端登记确定，客户端只提交待访问的标识。
- 计划新增 `/v1/resource-keys/` 路径族，承载构建注册、请求挑战和授权领取。构建注册沿用现有构建身份，运行时沿用现有设备批准或 App Attest 身份。先在自有服务仓库固定实际路由、请求和响应字段、错误码、限制以及跨语言测试向量，再接两个客户端。保留 `/v1/keys/*` 的请求、响应、授权语义和旧客户端错误兼容。
- 注册用应用构建和资源组作为幂等边界。同一请求重试返回相同结果，同一标识对应不同注册内容时报告冲突。构建成功后才发布产物和报告；若服务注册成功但本地构建失败，保留可重试记录，按现有服务运维机制处理孤儿注册。
- 请求证明绑定服务器挑战、应用身份、构建、资源组、资源版本、会话和当前响应公钥。服务器消费挑战并验证授权及时性，再使用既有密钥信封协议或经验证的系统加密接口返回密钥。运行时校验收件上下文后使用。明确 TLS 失败、超时、已撤销、证明不可用、挑战重放和策略拒绝的错误语义。服务完成响应和缓存时保留相同的租户隔离。
- 首版许可在进程内短期有效。使用单调时钟检查本地有效窗口，服务端控制授予的最大有效期。单个资源组同一时间合并重复取钥；其他资源组独立处理。并发请求、取消、超时、进程退出和再次进入均有可验证的状态。资源授权读取允许被取消，授权失败时默认仅拒绝对应受保护功能。
- 撤销阻断后续授权；客户端在本次许可到期后或收到明确拒绝时清除自身的新读缓存并停止发起新的受控读取。已复制的密钥和已交给下游组件的明文需按暴露处理。泄漏处置按受影响资源组生成新密钥、新资源版本和新密文，并明确旧密文的处置范围。首版要求联网领取授权；离线许可携带窗口和撤销延迟，留到有独立业务验收时再讨论。
- 取舍：同组密钥让同一份签名包可发布给多设备，泄漏范围仍包含该组的密文。更细的资源组或服务端按会话交付内容适用于确有更严隔离需求的资产。

### 运行时事件与动作

| 事件来源 | 可记录的信息 | 首版动作 |
|---|---|---|
| 资源及签名检查 | 资源 ID、构建、失败阶段、完整性结论 | 拒绝相关读取，保留可排障错误。 |
| 自有服务 | 设备授权状态、证明结果、授权签发或拒绝及关联请求 ID | 按资源组执行签发、拒绝或要求重试。认证失败与网络不可用使用独立原因。 |
| Android / iOS 本地运行时 | 调试、运行时异常、系统支持的捕获状态等信号，以及来源、阶段、时间 | 新信号先以记录验证误报。启用策略后，高置信证据限制对应敏感业务；系统截图或录屏按该页面的策略响应。 |

事件字段限定为版本、来源、类别、阶段、置信级别、资源组、短期关联 ID、策略版本、决定和结果。常规事件去重并限流。分别记录服务器已验证、本地已观察、当前不可用等状态。日志与报告过滤密钥、证明原文、持久设备标识、资源内容和绝对路径。应用透传的本地信号是辅助依据，服务器授权以已验证身份、请求绑定和设备状态为准。静态反编译、未产生应用内信号的内存读取等只能通过受控测试评估实际暴露范围。

- [ ] 保存可合法重放的正式历史测试 APK/IPA、产物摘要、签名/应用身份、实际运行时版本、发版参数、最小业务数据、对应 BYOS 测试 token 的来源和授权状态。凭据、原件和原始日志存入本地受控目录，Git 保存脱敏清单及引用。

- [ ] **出口**：旧客户端请求在新服务上通过基线，资源请求在测试服务通过正常和拒绝路径，跨平台使用相同版本的测试向量。

- [ ] 接入显式的受保护流式读取 API，在业务首次访问时申请授权，沿用现有设备签名和网络配置。首版小资源按需读取，避免把完整资源写盘，并将 BYOS 请求与 UI 主线程隔离。旧 `MocikaAssets.openFd`、Native overlay 和旧缓存键保持兼容。

- [ ] **出口**：受保护夹具在真机通过，检查 APK 无必保资源明文副本；旧 APK 原样启动与同签覆盖升级均达到基线。

- [ ] **出口**：每种新增方式都有对应真实消费者的业务回归与最终分发证据，报告准确标记密文、运行中明文和必要落盘路径。

## 每次改动的兼容验证和发布门禁

改动前在 PR 说明列出受影响的旧格式、旧配置、运行时 ABI、签名、密钥接口、缓存、业务数据和发布渠道。按变更实际触及的路径复用设备矩阵。每次发布保留旧签名产物作为下一轮输入。旧包原样测试和旧包覆盖升级是两个独立用例。

| 必查路径 | 验证输入与动作 | 通过条件 |
|---|---|---|
| 旧 APK / IPA 原样运行 | 直接使用历史产物。服务更新前后分别运行首启、缓存启动、已批准与撤销。 | 历史行为一致，同一旧 token 能获得原 IKM，资源读取和既有拒绝符合原契约。 |
| 旧包覆盖升级 | 从原 APK 或源码构建新包，保留应用身份、授权资料和分发签名关系；使用旧包准备业务数据后直接升级。 | 首次与二次启动均成功，原业务数据、账户及关键功能可用。Android 走同签正常版本升级，iOS 保留适用的 Team ID、Bundle ID、Keychain 权限和 App Group。 |
| 旧配置配新工具 | 在不启用新资源功能的工作流里，使用旧配置构建和签名。 | 与历史支持范围一致。测试旧输出的必要功能以及严格 PAS2、`openFd` 和 Native 读取。 |
| 新协议负面输入 | 篡改、截断、重复或交换分片，跨构建/跨组请求，过期、并发重放、撤销及网络错误。 | 必保资源认证失败不返回相应明文。拒绝只有受影响资源的读取。缓存不留下失败产物。 |
| 兼容回滚 | 用旧测试数据库演练增量迁移、服务版本回退、资源授予策略回退与客户端修复升级。 | 保留历史密钥和授权记录；已发布旧、新客户端均能获得各自协议的服务，或者使用可正常覆盖的修复版本恢复对应能力。业务数据得以保留。 |

执行时先复用下面的入口。新协议和资源容器各保留最小可运行回归，以固定测试向量覆盖新旧版本分流和篡改拒绝。新增的发布检查至少包含一条冻结历史产物在新服务上的回归和一条旧包保留数据覆盖升级的回归。设备测试使用专门的测试包名和签名材料。

```bash
make test
make build-stub
make build-byos
make build-byos-play
bash tests/scripts/run-protect-e2e.sh
```

`run-protect-e2e.sh` 缺少设备参数时只验证构建链。取用[回归清单](../process/test-checklist.md)里的真机参数、[兼容性矩阵](../process/compatibility-matrix.md)的设备入口和[BYOS 验证记录](../process/byos-local-validation.md)的服务场景。iOS 依次执行现行预检、Archive、Export、最终签名核验和真机验证。记录命令、日期、构建与产物摘要、设备、应用版本、密钥策略和场景结果，保留失败及未验证项。

以下情况阻止发布受影响的能力：已支持的旧产物无法启动或读资源、旧授权被意外改变、覆盖安装丢失业务数据、必保资源带有明文副本、认证失败后仍能读取目标资源、适用的性能预算失守。缺设备、签名或真实渠道时保留对应格子待验证，发布支持范围以已经取得证据的路径为准。

## 服务部署与回退顺序

1. 在含历史记录的测试环境完成数据库备份、迁移和旧包原样测试。保存回退所需的完整历史密钥材料与配置引用。
2. 先发布支持旧、新协议的服务，旧客户端按旧路由和策略继续运行。完成取钥探测和旧包验证，再允许新构建向资源服务注册。
3. 先在受控 Android 和 iOS 产物打开功能，检查资源授权错误率、P95 时延、业务失败和报告完整性。验收签名、覆盖升级与兼容矩阵后，发布对应的显式配置。
4. 出现异常时，先停止新注册和新产物分发。保留在用客户端所需的接口和密钥版本，按照故障点恢复服务实现或策略。涉及已分发客户端时，用保持应用身份且符合渠道升级规则的修复版本恢复。受保护资源继续按认证和授权策略读取。
5. 恢复后重新验证旧包原样、旧包升级、新包首次读取和设备撤销。保留三类产物的证据，再恢复新注册。

**开始执行时的第一个交付**是带摘要的旧产物清单、两个平台各一份小型自有资源夹具，以及跑过旧 `/v1/keys/*` 取钥的兼容基线。接下来提交资源格式测试向量和新旧协议并行的服务测试，再接 Android 与 iOS 的实际读取路径。
